# relora — ReLoRA alone and inside MOSAIC, plus a download/upload budget for SOLO vs MOSAIC

Files: `methods/relora.py`, `methods/mosaic_relora.py`, `bandwidth.py`,
`arms/relora.txt`. Logs in `logs/rl-*.log`, results in `results/rl-*.json`.
No harness edit was needed: `harness.py` loads `methods.<name>` by import, so a
new file under `methods/` is a new method. `methods/mosaic.py` is untouched
(`mosaic_relora.py` subclasses it).

## Why

The upstream author: "SOLO is an issue, as it requires more downloads
(activations)", and it was unclear whether SOLO would work with ReLoRA. This
note answers both with arithmetic from the code's own byte formulas and with
small runs on the 10m preset.

## Methods

### `relora` (Lialin et al. 2023, arXiv 2307.05695)
- Full-rank warm start for `warm` steps (default 10% of `total`), then every
  block linear (qkv, o, up, gate, down) becomes W = W0 + s·B·A with W0 frozen
  (a `torch.nn.utils.parametrize` parametrization, so the model code is not
  changed). A ~ N(0, 1/n_in), B = 0, s = alpha/r with alpha = 32 (s = 1 at
  r32, 0.25 at r128). A first r128 run with s = 1 went unstable after the
  switch to LoRA (eval 5.78 at 1.3M tokens rose to 5.94 at 3.3M; full rank
  was 5.25 at 4.1M) and was stopped at 5.5M tokens; its partial log is
  `logs/rl-r128-s1.log`. `rl-r128` was re-run with s = 0.25.
- Every `every` steps: merge s·B·A into W0, re-draw A, zero B, prune 99% of
  the adapters' AdamW moments by magnitude, and restart the LR with a linear
  re-warmup of `rwarm` steps under one global cosine (jagged schedule).
- Embedding (tied head) and RMSNorm gains stay full-rank and trainable.
- `rank=0` is the full-rank control with the identical warmup + cosine
  schedule (`wu` = 100, cosine to 0.1 × lr).
- Simplified: one worker; no 8-bit optimiser; because LoRA is a
  parametrization, autograd still forms the dense dW, so backward compute is
  the same as full rank (a real LoRA kernel saves the frozen-weight dW,
  about a third of linear-layer FLOPs). `up` is counted as 4 bytes per
  trainable parameter per step (a dense fp32 all-reduce of what is trained).
- Checked: merge-and-reset leaves the model output bit-identical
  (max |Δlogit| = 0.0 on a CPU check).

### `mosaic_relora` (MOSAIC with LoRA workers)
- Runs `warm` rounds of plain MOSAIC (full-rank), then every worker trains
  LoRA adapters on the block linears of its own module (including its local
  head's block); embedding, head, norms and τ stay full-rank.
- Merge-and-reset happens every round (ReLoRA reset interval = H = 30):
  at round start the frozen W0 is the broadcast round weights, adapters are
  reset (A from a seed shared by all workers of that round and module, B = 0),
  AdamW moments of the adapters are pruned 99%, the inner LR re-warms over
  `rwarm` = 5 steps. After H steps the module delta is exactly −s·B·A.
- Upload modes:
  - `up=product`: the dense rank-r product goes through MOSAIC's SparseLoCo
    compressor (chunk Top-64/4096, 2-bit, error feedback). Bytes = MOSAIC's.
    The server averages products.
  - `up=factors`: bf16 A and B are uploaded, r·(m+n)·2 bytes per matrix; the
    server multiplies each worker's factors and averages the PRODUCTS (exact
    up to bf16).
  - `up=factoravg`: the wrong-on-purpose ablation (arXiv 2601.00566 caution):
    the server averages A and B separately and applies s·mean(B)·mean(A).
- Measured bytes match `bandwidth.py`: 10m K=2 MOSAIC mean upload 0.138 MB per
  worker per round (harness `upPerWorkerMB` 0.138); factors r32 1.238 MB
  (harness 1.238).

## Bandwidth accounting (task 1)

Generated by `../../.venv/bin/python bandwidth.py` (W = 8 peers, H = 30).
Definitions, per volunteer per round:
- **DiLoCo dense**: download and upload the full bf16 model (2P bytes each;
  the lab's dense arm uses fp32, twice this).
- **SparseLoCo**: upload one compressed pseudo-gradient (116 bytes per 4096
  values + bf16 1-D tensors ≈ 0.23 bits/param); download every peer's message
  (Covenant object-store model) capped at the dense bf16 model: min(W·msg, 2P).
- **SOLO pipeline crew**: a volunteer holds one module of a K-stage pipeline;
  every inner step it receives the input activations and sends its output
  activations, seq·batch·d·2 bytes (bf16) per boundary, forward only (no
  gradient crosses a SOLO boundary), × H steps. The first stage only sends,
  the last only receives, middle stages (K ≥ 3) do both. Plus the same
  per-module weight sync as MOSAIC with its stage-peers in other crews.
  "ResBM 64x" divides the activation term by 64.
- **MOSAIC**: worker k must hold modules 0..k (embedding + earlier blocks, not
  the earlier local heads) plus its own module and W̄ (V·d) if k < K−1.
  Download either (i) those weights in bf16 every round (a fresh or rejoining
  volunteer), or (ii) the compressed uploads of the W/K peers of each needed
  module since last round (a volunteer that stayed in sync), capped at (i).
  Upload = SparseLoCo-compressed delta of its own module only.
- **MOSAIC+ReLoRA**: download as MOSAIC. Upload either the compressed product
  (= MOSAIC bytes) or bf16 factors (r·(m+n)·2 per adapted matrix, plus the
  compressed full-rank tensors: embedding/head, norms).

Real setting = seq 2048 × batch 8; lab = seq 128 × batch 8. (seq 2048
exceeds the 10m/100m presets' context length; that row is arithmetic only.)

Per volunteer per round; H=30 local steps, W=8 peers; MB = 1e6 bytes.

Reading the compute table: "worker k" is forward-equivalents per inner step
for the worker owning module k (one full backprop step of the whole model is
3.00). The "redundant prefix forward" column is the part of that spent
re-running modules 0..k−1 without gradients — the price of shipping no
activations. For K = 4 the last worker spends about 0.8 of its ~1.4 on the
redundant prefix (over half its compute), but still less per step than full
backprop (3.0). Averaged over the crowd, a token costs 0.43–0.69 of a
backprop step, because each token trains only one module. That number says
nothing about how much a token teaches the model; that is what the loss
results measure.

## Limits

- Tiny models (7M and 116M parameters), one seed, one Mac (MPS, fp32), short
  runs (10M and 4M tokens). Differences under ~0.03 in eval loss are within
  what a second seed could move.
- MOSAIC is simulated: workers run one after another on one GPU, so wall time
  is not a crowd's wall time.
- ReLoRA here uses a parametrization, so it saves no compute and only
  optimizer-state memory in principle (not measured). LoRA scale, LR and
  reset interval were not tuned (one 3-round smoke, then the arms).
- `factoravg` uses a shared A seed per round, the most favourable case for
  factor averaging; with independent A per worker it would be much worse.
- Download numbers assume an object store that serves every peer's message;
  at large W the per-volunteer download is capped by the dense bf16 model
  unless an aggregator re-sparsifies the merged update (not built here).
