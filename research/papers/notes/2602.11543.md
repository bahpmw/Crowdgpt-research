# 2602.11543 — Pretraining A Large Language Model using Distributed GPUs: A Memory-Efficient Decentralized Paradigm (SPES)

## 1. Citation

- **Title:** Pretraining A Large Language Model using Distributed GPUs: A Memory-Efficient Decentralized Paradigm
- **Authors:** Jinrui Zhang, Chaodong Xiao, Aoqi Wu, Xindong Zhang, Lei Zhang (The Hong Kong Polytechnic
  University; OPPO Research Institute)
- **Date:** arXiv v1 12 Feb 2026 (checked on the abs page). Notes are from v3 (15 Jun 2026). Preprint, no venue.
- **Code:** https://github.com/zjr2000/SPES (stated in the abstract; repository not inspected). Models said to be
  released (§1).
- **Name:** SPES = SParse Expert Synchronization.

## 2. Summary

DiLoCo-style training (each worker runs many local optimizer steps, then workers average their parameter
changes) cuts bandwidth, but every worker still trains, and keeps optimizer state for, the whole model. SPES applies
it to mixture-of-experts (MoE) language models, where each token uses only a few of many feed-forward "experts".
Each node **owns a disjoint subset of experts**. It trains the shared (non-expert) parameters plus only its own
experts, keeps all other experts frozen, and uploads only what it trained. A server averages the shared parameters
(FedAvg, federated averaging) and takes each expert from its single owner. Each expert now sees only its owner's tokens,
so an early **expert-merging warm-up** pulls each expert toward its most similar peers. Results: a 2.1B-total MoE
trained on 16 single-GPU (48 GB) nodes, a 7.3B MoE on 4 eight-GPU nodes, and a 9.4B MoE upcycled from a dense
checkpoint, all close to centrally trained baselines.

## 3. Method

1. **Model (§3.2):** decoder-only MoE with RoPE, SwiGLU, RMSNorm, QK-norm, dropless MoE and softmax top-k routing.
2. **Ownership (§3.3, Eq. 3):** split the M experts into N disjoint sets Φ_i, one per node. The shared parameters ψ
   (attention, embeddings, norms, router) are trained on every node. Each node keeps a **full copy of all weights**
   (frozen experts are still used in the forward pass). Gradients and AdamW state exist only for ψ and Φ_i.
3. **Local round:** start from the global model and run H AdamW steps on the node's shard. Shards are sampled
   independently and identically distributed (IID) from the whole dataset (§4.1).
4. **Sync (Eq. 4):** ψ ← mean of the nodes' ψ_i. Each expert is copied from its owner, with no averaging. There is
   no outer momentum. A custom gRPC server then broadcasts the merged model.
5. **Expert-merging warm-up (Eq. 5–6):** every T_i = 300 steps during the first T_w = 12,500 steps, find the K = 4
   experts whose input projections are most similar (cosine) and apply φ_j ← φ_j + α·mean_k(φ_k − φ_j), with
   α = 0.1 decaying linearly to 0.
6. **Hyperparameters (Table A1, App. B):** H = 100 for the 2B/7B/9B runs and 50 for 1B. The from-scratch runs switch to
   H = 50 with half the per-node batch after 70% of tokens. Peak learning rate 5e-4 (1B/2B), 4e-4 (7B), 1e-4 (9B).
   AdamW (0.9, 0.95), weight decay 0.1. Loss = cross-entropy + 0.01 load balancing + 1e-3 MoE z-loss + 1e-5 z-loss.
7. **Cost formulas (§3.3):** node memory is 4(|ψ|+|Φ|) for DiLoCo vs 4|ψ| + |Φ| + 3|Φ_i| for SPES. Per-round traffic
   is 2N(|ψ|+|Φ|) vs N(2|ψ| + |Φ| + |Φ_i|). Every node still **downloads all experts** each round.
8. **Theory (App. A, Thm. 1):** under smoothness and bounded-variance assumptions, the shared block gets 1/N
   variance reduction and the expert blocks do not (one owner each). Non-IID data adds a bias term ζ²_Φ. Warm-up
   merging adds a term that vanishes over training.
9. **Configs (Table 2), active/total parameters:** 0.3B/1.1B (16 experts, top-2), 0.8B/2.1B (16, top-2), 1.6B/7.3B
   (32, top-4), 3.1B/9.4B (8, top-2). The 9B starts from Qwen3-1.7B-Base: copy the FFN (feed-forward network) 8×,
   add noise (std 0.02) to 50% of the parameters, and renormalize the gates after top-k (§4.1).

## 4. Key reported results

- **Setup (§4.1):** 2B on 16 nodes × 1 NVIDIA L40S (48 GB) over **17 Gbps Ethernet**, one expert and about 0.7B
  trainable parameters per node. 7B on 4 nodes × 8 A800 GPUs over **13 Gbps Ethernet**, 8 experts and about 2.5B
  trainable per node. 2B and 7B trained on 500B tokens; the 9B on 400B (Table 3).
- **Memory per GPU (Fig. 3a,c):** 2B: centralized 54.5 GB, DiLoCo 54.5, SPES 34.1. 7B (sharded across 8 GPUs
  within a node): 43.1 / 43.1 / 41.0.
- **Upload per node per round (Fig. 3b,d):** 2B: DiLoCo 8.3 GB vs SPES 2.8 GB. 7B: 28.6 vs 9.8 GB (−65%). The
  "33.3% less communication" headline counts upload plus download (it matches the §3.3 formula; our check).
- **Controlled quality, 1B MoE, 50B SlimPajama tokens (Table 1):** 8-task average: centralized 50.02, DiLoCo
  49.79, SPES 50.95. Without expert merging, SPES scores 48.99 (Table 4).
- **Ablations, 1B:** 2/4/8 nodes at a fixed global batch score 50.6/49.7/49.5 (Table A5). H = 50 is best, and
  quality falls at H = 200 and 400 (Fig. A2). Warm-up settings peak at α = 0.1, K = 4, T_i = 300, T_w = 12.5k
  (Fig. A1).
- **Throughput (§4.2):** centralized training over RDMA (remote direct memory access, InfiniBand) reaches 3.79k
  tokens/s/GPU; SPES reaches 3.67k with H = 50.
- **Uncontrolled comparisons (Tables 3, A4):** SPES-2B: ARC-e 63.8, PIQA 69.3, MMLU 25.5. SPES-7B: ARC-e 72.1,
  PIQA 74.7, MMLU 24.9 (near chance). SPES-9B (upcycled): ARC-e 81.5, PIQA 78.9, MMLU 63.7, C-Eval 44.7.

## 5. Relevance to Crowd

- **Matches the v2 "path trainer" role** for sparse epochs (`archived/crowdgpt-v2/05-scale-roadmap.md` §5.2). A
  volunteer owns a few experts, trains the shared trunk, and uploads only what it trained. Optimizer memory grows with
  the experts a node owns, not with the total expert count. That is how a growing expert pool could map onto a
  growing volunteer pool.
- **Compression is unused, so it is free headroom.** The upload sizes imply about 4 bytes per parameter (0.7B ×
  4 B ≈ 2.8 GB; our inference). At 40 Mbit/s, 2.8 GB takes about 9 minutes per round (our arithmetic). Adding
  SparseLoCo-style top-k plus 2-bit compression (over 146× in Covenant-72B, 2603.08163) could bring that to tens of
  MB (untested). The **shared trunk dominates the upload**: about 0.61B of the 0.7B trainable parameters per node at
  2B (our arithmetic from §4.1 and Table 2). Compress the trunk first.
- **The memory floor is not solved for E4.** SPES keeps every expert in memory. A ~27B MoE needs about 54 GB in
  bf16 (16-bit) for weights alone (roadmap table), which is beyond 8–24 GB cards. Options: (a) FoMoE (2606.19025) skips tokens
  routed to experts the node does not hold. (b) Keep non-owned experts in 4-bit, read-only form (our idea,
  untested). (c) Send whole documents to nodes that hold that document's expert pool (EMO, 2605.06663).
- **Composes with Decoupled DiLoCo (2604.21428).** Its quorum-based asynchronous syncer could replace the
  synchronous SPES server, and it already reported MoE runs. The 9B result shows dense→MoE upcycling inside a
  decentralized loop, which is relevant to the E3→E4 pivot (but see 2604.19835, Table 4).
- **Trust:** each expert has exactly **one writer** and is never averaged. That makes updates easy to attribute, but a
  dishonest owner fully controls its expert, and a dropout orphans it. Crowd would need replicas per expert, with
  robust averaging across replicas (Soft Throttling 2609.39357 style). It would also need per-expert scoring, such as
  Covenant's Gauntlet LossScore restricted to tokens routed to that expert. Robust averaging on the trunk alone is
  not enough.
- **vs SOMA (2609.37899):** SOMA's experts are fully independent (no shared trunk, ensembled at inference). SPES
  keeps one routed model but pays for syncing the trunk every H steps.

## 6. Caveats

- "Over internet connections" means 13–17 Gbps Ethernet (§4.1), about 130–850× a 20–100 Mbit/s home uplink. Home
  links, latency, NAT (home-router address translation), churn and stragglers are untested. Rounds are synchronous
  through one server.
- At most 16 nodes. Quality drifts down as node count rises (Table A5). Data is IID per node; GPUs are homogeneous.
- Experts have a single owner and no redundancy. There are no fault-tolerance or Byzantine experiments.
- The memory saving covers only gradient and optimizer state. All weights stay resident, so the 7B saving is small
  (43.1→41.0 GB).
- Only the 1B/50B-token comparison is controlled; seeds and run-to-run noise are not reported (unverified).
  Tables 3/A4 compare against models with different data and token counts. The 9B's strong scores
  mostly reflect its Qwen3 initialization, which was trained on 36T tokens (Table 3).
- Backprop with AdamW only. No zero-order (DUST) or compressed-communication experiments. The paper states that
  ChatGPT-5 helped with editing (App. F).
