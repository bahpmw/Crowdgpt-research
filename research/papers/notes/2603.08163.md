# 2603.08163 — Covenant-72B: Pre-Training a 72B LLM with Trustless Peers Over-the-Internet

## 1. Citation

- **Title:** Covenant-72B: Pre-Training a 72B LLM with Trustless Peers Over-the-Internet
- **Authors:** Joel Lidin, Amir Sarfi, Erfan Miahi, Quentin Anthony, Shivam Chauhan, Evangelos Pappas,
  Benjamin Thérien, Eugene Belilovsky, Samuel Dare (Covenant AI; Mila)
- **Date:** arXiv v2, 10 Mar 2026 (cs.DC)
- **arXiv id:** 2603.08163
- **Built on:** SparseLoCo (Sarfi et al., arXiv 2508.15706) and Gauntlet (Lidin et al., DAI 2025, ref [23]).
  This report gives a summary of both. The full specifications are in those papers, which were not read here.

## 2. Summary

Covenant-72B is a technical report on a permissionless, blockchain-coordinated (Bittensor Subnet 3) pre-training
run. It trained a 72.7B dense LLaMA-3-style model on about 1.1T tokens over commodity internet. Each peer
(at least 8×B200) runs H=30 local AdamW steps. It then sends a *pseudo-gradient*: the parameter delta, compressed
with chunk-wise Top-k (64 of every 4096 values), 2-bit quantization, and error feedback (decay β=0.95). The
result is more than 146× smaller than dense communication. A validator (Gauntlet) scores each submission
mainly by **LossScore**: the loss before minus the loss after applying that peer's update on a small batch.
Peers are ranked over time with OpenSkill. The top submissions are selected (cap 20 per round), each is
rescaled relative to the median norm, then averaged. All peers apply an outer step with α=1. Communication
goes through object storage (Cloudflare R2), not peer-to-peer links. The report claims 94.5% compute
utilization (70 s of communication per 20-minute round) and benchmark scores competitive with LLaMA-2-70B
and LLM360 K2.

## 3. Algorithm

### 3.1 Symbols
- `R`: set of workers selected this round. `|R| <= 20` (cap); 16.9 on average.
- `θ(t)`: global parameters at outer round t. Every replica holds the same copy.
- `θ_r(t,h)`: worker r's local parameters after h inner steps, starting from `θ_r(t,0) = θ(t)`.
- `H = 30`: inner steps per round.
- `D_r`: worker r's assigned data shard. Shards may overlap.
- `e_r(t)`: per-worker error-feedback buffer, same shape as θ, initialized to 0.
- `β = 0.95`: error-feedback decay.
- `TOP-k`: chunk-wise Top-k by magnitude, with C=4096 positions per chunk and k=64 kept per chunk
  (density 1/64 ≈ 1.56%). 2D tensors are split into non-overlapping 64×64 blocks. 1D tensors are split into
  contiguous chunks of 4096.
- `Q`: 2-bit quantizer applied to the kept values. The paper does not give the exact scheme.
- `α`: outer learning rate. It is 1.0 for most of the run, lowered to 0.65 late in training. There is no outer
  momentum; the outer step is plain SGD.

### 3.2 Per-round update (Eq. 1–2)
```
# worker r, round t
θ_r ← θ(t)
for h in 1..H:  θ_r ← AdamW_step(θ_r, ∇L(θ_r; batch from D_r))
Δ_r   = θ(t) − θ_r                              # pseudo-gradient (descent direction)
acc   = β·e_r + Δ_r
Δ̂_r   = Q(TOPK_chunk(acc))                      # sparse + 2-bit
e_r   ← acc − Δ̂_r                               # residual includes quantization error
upload (indices, 2-bit codes, per-chunk scales?) to object store

# validator: score each submission, choose selected set R (top scorers)
# every replica:
Δ̂_r ← Δ̂_r · (median_r' ||Δ̂_r'|| / ||Δ̂_r||)  # "scaled relative to median norm" (exact form unspecified)
Δ    = (1/|R|) Σ_{r∈R} Δ̂_r
θ(t+1) = θ(t) − α·Δ
```
Error feedback is per peer and stays on the peer. A peer that is not selected still updates `e_r` locally, as
written in Eq. 1. The report does not say whether a non-selected peer's residual is credited.

### 3.3 Compression accounting
- Values: 2 bits. Indices: 12 bits per value (log2 4096, no entropy coding). The information-theoretic bound is
  about 7.36 bits per value: (1/k)·log2 C(4096,64).
- Bits per parameter ≈ (2+12)·64/4096 = 0.219, so 32/0.219 ≈ 146×. This matches the stated ">146×" if the
  baseline is fp32 dense.
- On top of that, there is one communication per H=30 steps.

### 3.4 Gauntlet (validator) — as summarized in this report
1. **LossScore**: for a subset of peers, on a small batch, compute `L(θ) − L(θ − α·Δ̂_r)`.
   Higher is better.
2. **Assigned vs. unassigned check**: compute LossScore on the peer's assigned data and on random unassigned
   data. If the update improves random data *more* than assigned data, the peer gets a **negative** score.
   This targets copying and duplication.
3. **Fast checks** on all peers: liveness, synchronization with the current global model, and similar.
4. Signals are combined into a persistent **OpenSkill** rating. This smooths out per-round sampling noise.
5. **Selection**: the top-scoring peers form `R`. The system keeps slightly more active peers (24.4 on average)
   than contributors (16.9 on average) so that dropouts are replaced quickly.
6. **Median-norm rescaling**: no single submission can dominate because of its magnitude.

## 4. Key reported results

- **Utilization**: 20-minute compute and 70 s communication per round, so about 94.5%. For comparison,
  INTELLECT-1 (10B, H=100, about 14 peers) had 38 min compute and 8.3 min communication (82.1%). SparseLoCo
  on 8B (R=15, H=30) had 4.5 min compute and 12 s communication (95.7%).
- **Participation**: 24.4 active and 16.9 contributing peers per round on average; at least 70 unique peers
  over about 6,190 outer steps.

## 5. Classification for Crowd v1.5

**Mainly a complement to DUST.** It also becomes a *replacement* if clients can afford local backprop.

- **Communication bytes**: this is the strongest fit. Chunk-wise Top-k (64/4096) plus 2-bit quantization plus
  error feedback (β=0.95), at about 0.22 bits per parameter, can wrap DUST's compressed gradient uploads
  directly. Error feedback is particularly relevant: DUST estimates are noisy, so EF keeps the dropped mass
  across rounds instead of discarding it.
- **Byzantine / untrusted peers**: LossScore is itself a zeroth-order loss-difference test. That is the same
  primitive DUST already computes, so the coordinator can validate uploads the same way. The assigned-vs-random
  data check and median-norm rescaling are cheap additions.
- **Dynamic participation**: over-provisioning active peers relative to contributors.
- **Compute per useful step / low gradient cosine**: H=30 local AdamW steps per communication gives a far
  better signal per byte than a per-step ZO estimate. If clients can backprop a small model, this paradigm
  *replaces* DUST's estimator. It does not fix the ZO variance problem itself.
- **Not addressed**: consumer-GPU memory. Their peers are 8×B200 with FSDP, plus CPU offload of the EF buffer.

## 6. MVP recipe (M5 Max, MPS, PyTorch 2.15, about 2–10 min)

**Setup:** a 7M-parameter GPT (vocab 4096, seq 128, real FineWeb-Edu tokens). Simulate R=4–8 workers
sequentially on one device. Each worker has its own data shard (disjoint token-stream offsets) and its own
EF buffer. Use a fixed token budget per arm, sized so the AdamW baseline takes about 2 minutes; measure
throughput first. Log `val_loss` vs. tokens consumed (summed over workers), vs. wall time, and vs. bytes uploaded.

**Arms:**
1. `adam`: single-process backprop AdamW with global batch = R × per-worker batch (DDP-equivalent).
2. `diloco_dense`: H=30 inner AdamW, uncompressed Δ averaged, outer SGD α=1 (and a Nesterov variant).
3. `sparseloco`: arm 2 plus chunk Top-k (k=64/C=4096; 64×64 blocks for 2D) plus 2-bit Q plus EF β=0.95.
4. `dust`: the current DUST estimator with the existing coordinator SGD+momentum.
5. `dust+sparseloco_comp`: DUST per-client estimate pushed through the same EF+TopK+Q pipeline. This is the
   complement test.
6. (Robustness) Arm 3 with 1 of 8 workers malicious: sends −10·Δ, or a random vector at 10× median norm, or
   a copy of another worker's Δ. Compare a plain mean with LossScore selection (top R−1 of R by loss
   difference on 2 held-out batches) plus median-norm rescaling.

**Minimal pieces to implement:**
- `chunk_topk(t, C=4096, k=64)`. For 2D tensors, reshape to blocks of 64×64 (pad the edges). For 1D, use
  `view(-1, 4096)`. Use `topk(abs)` per row and return (idx int16, val).
- `quant2bit(val)`. **This is our assumption; the paper does not specify it.** Use a per-chunk scale
  `s = mean|val|`, encode the sign plus 1 magnitude bit with levels {±0.5s, ±1.5s}, dequantize to centers.
  Alternative: sign × per-chunk mean-abs. Report which one you used.
- EF buffer update exactly as in Eq. 1. The outer step is `θ -= α·mean(Δ̂)`.
- A byte counter: count 14 bits per kept value plus 32 bits per chunk scale.

**What "proves out" looks like:**
- `sparseloco` reaches within about 2–5% of `diloco_dense` val loss at equal tokens, at about 146× fewer
  bytes.
- `dust+sparseloco_comp` matches `dust` loss vs. tokens at much lower bytes. Ablate EF off to show that EF
  is what makes it work.
- With one Byzantine worker, the plain mean diverges or stalls while LossScore+median-norm stays within about
  1–2% of the honest run.
- Wall-time view: SparseLoCo's tokens per second per worker are about backprop speed. Compare loss at equal
  wall-clock against DUST, which needs forward passes per draw.

## 7. Caveats / unclear points

- The **2-bit quantizer** is unspecified: levels, scale granularity, stochastic or deterministic.
- The **median-norm normalization** formula is vague. Is it clip-to-median or rescale-to-median? Is it applied
  before or after selection?
- **Gauntlet specifics** are deferred to ref [23]: batch sizes, how many peers are evaluated per round, the
  OpenSkill update, and how fast-check signals are weighted.
- The EF interaction with **non-selected** peers is not described. Their residual may be "consumed" locally
  even though the update was never aggregated.
- Outer step is α=1 with no momentum. Most DiLoCo work uses Nesterov (lr≈0.7, μ≈0.9). There is no ablation
  here, and α was lowered ad hoc to 0.65.
- **No controlled baseline.** Benchmark comparisons use different data, tokenizers, and token budgets. The
  only claim against AdamW at matched data is unquantified.
- Peers are datacenter-class (8×B200). Nothing here tests consumer GPUs, heterogeneous speeds within a round
  (there is a fixed 20-minute window), or real adversarial pressure. The rate of attempted attacks is not reported.
- The validator cost (forward passes per scored peer) and its trust model (a single validator?) are not
  quantified.
- Compression ratio: "146×" appears to be relative to fp32 dense per communication. Relative to bf16 it would
  be about 73×.
