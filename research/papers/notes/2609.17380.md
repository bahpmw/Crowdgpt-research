## 2. Summary

Floating-point addition is not associative, so the same recipe on different hardware gives slightly
different weights. Nobody can check that a released checkpoint came from the declared data and recipe,
and tolerance-based checks such as proof-of-learning (PoL) cannot rule out a backdoor that needs only a
few poisoned samples (§1). OPEN-1B fixes every source of nondeterminism: kernel reductions (RepOps), data
order (a data stream that does not depend on cluster shape), and collective communication (deterministic
reduce-scatter and all-reduce). Any single step of a 48-GPU run can then be replayed **bit for bit** on one
commodity device (NVIDIA GPU, x86 or ARM CPU, Apple Silicon) and checked against a per-step state hash.
Many independent auditors each certify individual steps and together cover the run. The authors train
and release Open-1B (1.61B parameters, 400B tokens) this way, using int8 quantization-aware training (QAT)
to reduce the speed penalty of reproducibility.

## 3. Method

- **Bitwise reproducibility (BR), not just determinism** (§2): same bits across different hardware, not
  only on the same machine.
- **RepOps rules** (§2.1, Table 1): one fixed reduction order on every backend; one fused-multiply-add
  convention (fusion disabled on CPU, explicit unfused ops on GPU); subnormals flushed to zero everywhere
  (matching Apple GPUs, the least permissive backend); a counter-based random generator where value =
  f(seed, index), independent of how work is split. Averages use multiply-by-precomputed-reciprocal,
  because CPU division and CUDA's reciprocal differ by up to one unit in the last place (App. A.3).
- **Topologically invariant data stream** (§2.3): three pseudorandom generators seeded only by run
  constants pick the source, the shard order (seeded with a SHA-256 hash of the source name) and the
  document order. Fixed 4,097-token windows. Data-parallel rank r owns window m if m mod R = r. Changing
  the number of GPUs changes only which rank loads a window, never the token stream. The resume state is a
  small record that does not depend on rank.
- **Deterministic collectives** (App. A): intra-node reduce-scatter = all-to-all (pure data movement) plus
  a local sum in ascending rank order. Inter-node all-reduce = recursive-doubling butterfly; the replay
  uses **TreeFold**, a binary-carry fold that keeps the lower replica on the left of each addition and
  needs only O(log2 replicas) accumulators (spilled to disk). A single-device sum matches the reduce-scatter
  of NCCL (NVIDIA's collective communication library) only to about 1e-11 relative error, not bitwise (App. A.2).
- **Audit replay** (§6, Algorithm 1): replay every virtual rank's forward and backward pass in mesh order,
  accumulate micro-batches, add shards in ascending order, fold replicas, apply AdamW. Compare with the
  per-step sharded canonical hash (host-side blake2b) over each rank's data batches, parameters, optimizer
  state and gradient shards (App. B).
- **Model and recipe** (§3.1–3.2, Tables 2–4): Llama/OLMo-style, 24 layers, width 2048, grouped-query
  attention, sliding-window attention, z-loss. int8 weights and activations with learned step-size
  quantization (LSQ) on all attention/feed-forward linears; attention backward accumulates the query gradient
  in 64-bit fixed point. AdamW with FP32 moments, batch ramp 3.1M → 4.7M → 9.4M tokens/step, 48×H100.
- **Stability fixes forced by int8 + reproducibility** (§4): zero query gradients from int8 attention
  backward ("gradient creep"); LSQ step-size drift pushed the gradient norm above 300, fixed by recomputing
  step sizes from the weights every step (~2% of step time vs ~70% for dropping quantization).

## 4. Key reported results

- **Run and quality** (§3.4, Tables 6–9): 80,957 steps, 400B tokens, 27.8 active days in 7 segments (each
  restart validated by hash comparison on repeated steps). Final held-out cross-entropy 2.580; benchmark
  average 25.4 vs 31.9 for OLMo 2 1B (4T tokens). 10 steps skipped by the spike rule. Against PyTorch bf16
  with the same recipe and data order, the int8 loss diverges by about 0.2 nats after 400B tokens (§4.3).
- **Cost of reproducibility** (§5, Table 10; fixed 4.72M tokens/step, no hashing):

  | Nodes (8×H100) | PyTorch + compile, bf16 | RepOps bf16 | RepOps int8 (production) | PyTorch / int8 |
  |---|---|---|---|---|
  | 1 | 288k tok/s, 40.5% MFU | 23.6k, 3.3% | 42.1k, 5.9% | 6.8× |
  | 6 | 1,136k, 26.6% | 129.1k, 3.0% | 217.5k, 5.1% | 5.2× |

  MFU = model FLOPs utilization. The authors summarize the burden as "≈5× more than optimized PyTorch".
  Reproducible bf16 is about 1.6–1.8× slower than reproducible int8 (§4.3, §5).
- **Deterministic all-reduce** (804 MB bucket, Table 11): 1.13× NCCL's time at 2 nodes, 1.59× at 4,
  3.54× at 6 (non-power-of-two node counts need extra hops; the whole buffer is sent on each hop).
- **Scaling 1 → 6 nodes** (Table 11): 71% efficiency with a state hash every step, 86% without. The hash
  costs a constant ~6.0 s per step: 4.9%, 9.3%, 16.7%, 21.4% of wall time at 1, 2, 4, 6 nodes (App. B).
- **Released:** full 450.5B-token data mix (Table 5), checkpoints every 100 steps, code, audit harness (§7).
  **Not reported:** consumer-hardware replay time, auditor assignment, steps audited so far, attack tests.

## 5. Relevance to Crowd

- **Answers our "rounding-noise question"** (archived/crowdgpt-v2/02-trust-and-verification.md §3):
  bit-exact replay of a 1.6B pretraining step across GPU vendors, CPUs and Apple Silicon is demonstrated.
  With exact replay, a sampled check becomes a proof for that step, not a score. The tolerance band that
  broke proof-of-learning (03-prior-art §2.1) disappears.
- **The price is large.** About 5–7× slower than optimized PyTorch for the full training stack (Table 10).
  Our prior-art note (03-prior-art §2.2) cites Verde's RepOps at about 30–60% on large matmuls and about 60%
  on Llama-3.1-1B training. Baselines differ (OPEN-1B compares with torch.compile), so part of the gap may be
  the baseline (unverified). In a volunteer network, throughput is the scarce resource. Our analysis, untested:
  - require reproducible kernels only where exact audit matters: forward-only work (DUST, zeroth-order
    lanes), the optimizer step, and aggregation arithmetic;
  - audit within the same hardware class using cheap same-machine determinism (other sources report about
    2–8% overhead: arXiv 2606.05433 and an NVIDIA Megatron blog; not read in full, unverified), and use
    cross-vendor BR only for disputes;
  - adopt int8 QAT as the default if BR is required everywhere.
- **Directly reusable pieces:** (1) the topology-invariant data stream: the same tokens however many peers
  join or leave, which fits beacon-assigned shards and churn; (2) TreeFold, so independent orchestrators get
  bit-identical float aggregates whatever the arrival order (sort canonically, then fold), replacing our
  draft's fixed-point-sum idea; (3) the per-step sharded state hash as the "commit first" record (our layer
  L1) that auditors check (layer L2).
- **Audit grain:** a Crowd work unit (one peer's local steps on a small batch) is far smaller than a
  4.72M-token OPEN-1B step, so one audit on a consumer card costs much less (our inference). Apple Silicon
  support means volunteers without large GPUs could serve as auditors.
- **Round-1 links:** Covenant-72B/Gauntlet (2603.08163): LossScore becomes a cheap first filter, exact
  replay the proof. Decoupled DiLoCo (2604.21428): its token-weighted merging and quorum must run in
  canonical order to be auditable. Soft Throttling (2609.39357): robust aggregation bounds damage from
  contributions not yet audited. SOLO (2609.35440): a module step replays from signed inputs; BR makes it exact.
- **Million-GPU angle** (our analysis): audit cost scales with the sampled fraction, not with the number of
  peers; copied, partial or poisoned work is caught bit-exactly whenever its step is sampled.

## 6. Caveats

- RepOps is called proprietary (§7). An open, "verify everything" network needs an open implementation;
  whether the released code includes the RepOps source is unverified.
- This was a single trusted datacenter run (48×H100). There were no untrusted peers and no adversarial
  test of the audit. The "collective verification scheme" gets about one paragraph (§1, §6), with no
  auditor-assignment protocol, Sybil resistance or dispute procedure.
- The reproducible recipe changes model quality: the loss diverges about 0.2 nats from bf16, and the model
  trails OLMo 2 1B, though with 10× fewer tokens.
- MFU is about 5% (§5). Scaling is shown only up to 6 nodes, and the deterministic all-reduce premium
  already reaches 3.54× at 6 nodes.
- Replay assumes synchronous data-parallel training. DiLoCo-style local steps, top-k compression with
  error feedback, and asynchronous staleness add state that must also be made reproducible (untested).
- Consumer-hardware replay time and memory needs for a 4.72M-token step are not given (unverified).
